# B4 JVM Artifact Policy V1

## Status and claim boundary

`eip0045-b4-jvm-artifact-v1` is the closed inspection policy for the
JVM-lineage validator candidate (wire identifier `independent-jvm`) used by the
EIP-0045 B4 positive gate. The identifier is not an independence attestation.
This is an evidence-generation rule, not an Ergo consensus rule.

Its machine-readable projection is the JVM branch of the
[B4 validator build-descriptor schema](../../reproduction/finalizer-schema/b4-validator-build-descriptor-v1.schema.json).

The inspected artifact is an **executable JAR**. It is not described as
"self-contained": the Java runtime and its native libraries are supplied and
bound separately by the JVM execution runner profile. `classpathMode =
jar-only` means that the finalizer supplies no application class path other
than the exact JAR. It does not mean that Java platform modules are part of the
JAR.

The policy establishes complete archive parsing, complete class-file
structural parsing, direct symbolic-reference checks, and bounded byte-signature
checks on resources. It does not establish the absence of behavior reached
through reflection, generated bytecode, encoded or assembled symbols,
resource-selected delegation, or native code already present in the bound Java
runtime. Those are explicit source-review and runner-profile obligations.

## Normative Java target

The target runtime feature release is Java 21. Class files are interpreted
under the [Java SE 21 JVM Specification, Chapter 4](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html),
and the executable manifest under the
[Java SE 21 JAR File Specification](https://docs.oracle.com/en/java/javase/21/docs/specs/jar/jar.html).
Java 21's maximum class-file major version is 65.

Classic ZIP record names and integer layouts are pinned to PKWARE
[APPNOTE 6.3.10](https://support.pkware.com/pkzip/application-note-archives),
archived as `APPNOTE-6.3.10.TXT`. Later APPNOTE revisions do not silently
extend this policy. The rules below close every accepted field needed by B4;
the APPNOTE pin supplies record vocabulary, not permission to use another ZIP
feature.

Every observed class-file major version is recorded exactly. V1 accepts only
major versions 45 through 65 and minor version zero. Preview class files are
therefore outside this policy even when a particular Java 21 runtime could be
started with preview support.

## Inputs and fail-closed result

The inspector receives the exact JAR bytes whose `byteLength` and `sha256`
appear in `JvmArtifactIdentity`. It uses checked integer arithmetic and bounded
allocation throughout. Any malformed record, unsupported feature, exhausted
bound, inconsistent count, incomplete read, or policy violation rejects the
artifact; no partial inspection result is accepted.

The finalizer independently recomputes every inspection field from the exact
artifact bytes and compares it with the build descriptor before launch. The
following cross-field equalities are semantic checks, even though JSON Schema
cannot express them:

- `archive.entryCount == archive.localFileRecordCount`;
- `archive.entryCount == archive.regularFileEntryCount +
  archive.directoryEntryCount`;
- `archive.dataDescriptorCount` equals the number of entries with general
  purpose bit 3;
- `classFiles.classEntryCount` equals the number of regular names ending in the
  exact case-sensitive ASCII byte suffix `.class`;
- `classFiles.minimumObservedMajorVersion <=
  classFiles.maximumObservedMajorVersion`, and both are the extrema actually
  observed;
- `nonClassFiles.regularEntryCount ==
  archive.regularFileEntryCount - classFiles.classEntryCount`;
- `nonClassFiles.scannedEntryCount == nonClassFiles.regularEntryCount`;
- `manifest.mainClassEntry` is obtained by replacing every `.` in
  `manifest.mainClass` with `/` and appending `.class`.

## Canonical ZIP/JAR subset

The archive sub-policy identifier is `eip0045-b4-canonical-jar-zip-v1`.
Terms such as local file header, central directory header, data descriptor, and
end-of-central-directory record refer to their classic ZIP record layouts.
V1 deliberately defines a smaller accepted language instead of claiming
generic ZIP compatibility.

### Global bounds and record coverage

- The exact archive is at most 1,073,741,824 bytes.
- There are 1 through 65,534 entries. The value 65,535 is reserved rather than
  accepted as an ambiguous literal/sentinel boundary.
- The sum of decompressed regular-file sizes is at most 1,073,741,824 bytes.
- One decompressed entry is at most the same 1,073,741,824-byte total bound;
  the scanner streams data and does not allocate that amount as one buffer.
- File names are at most 240 bytes. Entry comments are not accepted. Extra
  fields are empty except for the optional exact JAR marker described below.
- The end-of-central-directory record is the final 22 bytes, has a zero comment
  length, uses disk number zero for both disk fields, and reports the same
  classic 16-bit entry count in both count fields. `0xffff` is always rejected.
  No 16-bit or 32-bit field may use its all-ones ZIP64 sentinel value.
- The central directory is one contiguous range immediately before the
  end-of-central-directory record. Its declared offset and size are exact.
- The first local file header starts at byte zero. Local records, compressed
  payloads, and any accepted data descriptors form one contiguous range ending
  exactly where the central directory begins.
- Every central directory entry points to one distinct local record, every
  local record has one central directory entry, and their ranges do not overlap.
  Central entries occur in exactly the same order as local records.
  No prefix, suffix, gap, digital-signature record, or other unreferenced byte
  is accepted.

The corresponding descriptor values are therefore zero for
`prefixByteLength`, `suffixByteLength`, `unreferencedByteLength`, and
`overlappingEntryCount`. `centralDirectoryOrderMismatchCount` is also zero.

### Unsupported ZIP features

V1 rejects:

- multi-disk archives;
- ZIP64 end records, locators, data descriptors, sentinel fields, and extra
  field `0x0001`;
- encryption, strong encryption, patched data, compressed metadata, and every
  general-purpose flag other than bit 3 (data descriptor) and bit 11 (UTF-8);
  bit 11 is mandatory for every entry, bit 3 is absent for stored entries and
  mandatory for DEFLATE entries;
- every local or central extra field except one optional JAR marker with header
  ID `0xcafe` and data length zero. If present, the marker occurs only on the
  first entry and appears identically in its local and central headers;
- archive and entry comments;
- compression methods other than stored (`0`) and raw DEFLATE (`8`);
- links and Unix special file types.

`zip64RecordCount`, `encryptedEntryCount`, `multiDiskFieldCount`,
`unsupportedFlagEntryCount`, `unsupportedExtraFieldEntryCount`,
`archiveCommentByteLength`, `entryCommentCount`, and
`linkOrSpecialEntryCount` must all be zero.

### Closed classic header fields

Local and central fields are accepted only under this Java-21-safe profile:

- stored entries have version-needed 10 and flags `0x0800`; DEFLATE entries
  have version-needed 20 and flags `0x0808`;
- central version-made-by has host byte zero and a low byte equal to the
  entry's version-needed value. Disk-start, internal attributes, and external
  attributes are zero. File type is therefore derived only from the canonical
  trailing slash, never from Unix mode bits or DOS attributes;
- the DOS date is `0x0021` and time is `0x0000`, exactly
  `1980-01-01T00:00:00` in the field's timezone-free representation;
- local and central file-name bytes are identical. Local and central extra
  bytes are both empty, except that the optional zero-length `0xcafe` marker
  may occur identically on the first entry; and
- every CRC, compressed size, uncompressed size, local-header offset, central
  directory offset, and central directory size fits its ordinary unsigned
  classic field without a sentinel.

The descriptor records zero `versionFieldMismatchCount`,
`nonCanonicalTimestampCount`, `utf8FlagMissingCount`,
`nonZeroAttributeCount`, and `centralDirectoryOrderMismatchCount`. A producer
may use an ordinary Java 21 `JarOutputStream`, but its output is accepted only
when these bytes are actually present; library provenance is not a substitute
for parsing them.

### Names and entry types

Names are interpreted from their exact bytes, not through a host filesystem.
Every name must be non-empty printable ASCII, use `/` as its only separator,
and be relative. A name is noncanonical if it contains a backslash, colon,
NUL, leading slash, empty segment, `.` segment, `..` segment, or a trailing
slash on a regular file. A directory marker ends in exactly one `/`, has zero
decompressed size and CRC-32 zero. It is either stored with compressed size
zero or DEFLATE-encoded as an exact empty stream.

Names must be unique byte-for-byte and also unique after ASCII-only lowercase
folding. This prevents a case-insensitive consumer from selecting a different
entry. `duplicateEntryNameCount`, `asciiCaseFoldCollisionCount`, and
`nonCanonicalEntryNameCount` must be zero.

The first local record and first central record are exactly
`META-INF/MANIFEST.MF`. All remaining names are strictly increasing by unsigned
ASCII byte order. `manifestFirstEntryCount` is one and
`canonicalEntryOrderMismatchCount` is zero. Because attributes are fixed to
zero, symlinks and Unix special types have no accepted representation. The
scanner does not extract the JAR.

### Local/central agreement, descriptors, and decompression

For every entry, local and central headers must agree on every duplicated field.
A stored entry has bit 3 clear; its local CRC-32 and sizes equal the central
values and no descriptor is present. A DEFLATE entry has bit 3 set; its local
CRC-32 and size fields are zero and exactly one 16-byte classic descriptor
immediately follows the compressed payload:

```text
0x08074b50 || crc32-le || compressed-size-u32-le || uncompressed-size-u32-le
```

The signature is mandatory. Unsigned and ZIP64 descriptors are rejected. All
three values must equal the central values. `dataDescriptorCount` records the
exact number accepted; `unsignedDataDescriptorCount` and
`zip64DataDescriptorCount` must be zero.

Stored data has equal compressed and decompressed sizes. A raw DEFLATE parser
must stream the declared compressed range exactly, reach end-of-stream, and
produce exactly the declared decompressed size without exceeding either the
per-entry or cumulative decompressed-byte bound. CRC-32 is recomputed over every
decompressed regular file. An entry with compressed size zero must also have
decompressed size zero. Header disagreements, CRC disagreements, size
disagreements, and decompression failures are separately counted and every such
count must be zero.

## Executable manifest and class path

The manifest sub-policy identifier is
`java-se-21-jar-manifest-executable-v1`.

- Exactly one regular entry is named `META-INF/MANIFEST.MF` with that exact
  case, it is the first archive entry, and its uncompressed length is 1 through
  65,536 bytes.
- The file is parsed completely under the Java SE 21 manifest grammar. It must
  be valid UTF-8, use CRLF line endings, end after a CRLF-terminated section,
  and obey the 72-byte bound for every physical line excluding its CRLF. The
  leading space of a continuation line counts toward those 72 bytes.
- Attribute names are checked ASCII-case-insensitively for uniqueness after
  continuation unfolding, but their accepted spelling and order are exact. The
  main section contains only `Manifest-Version: 1.0`, `Main-Class: <binary
  name>`, and optionally `Created-By: <printable ASCII>`, in that order.
  `Manifest-Version` is the first physical logical attribute. `Created-By`, when
  present, is at most 256 unfolded bytes. No individual named section follows
  the terminating empty line.
- `Main-Class` is present exactly once. Its binary name is at most 234 bytes so
  that the derived name plus `.class` remains within the 240-byte archive-name
  bound.
- `Main-Class` is a binary class name matching the schema. Its derived class
  entry exists exactly once as a regular `.class` entry.
- Every other main attribute is rejected by the allowlist. This includes
  `Class-Path`, `Multi-Release`, `Launcher-Agent-Class`, `Add-Exports`,
  `Add-Opens`, `JavaFX-Application-Class`, `Premain-Class`, `Agent-Class`,
  `Boot-Class-Path`, `Can-Redefine-Classes`, `Can-Retransform-Classes`,
  `Can-Set-Native-Method-Prefix`, `Signature-Version`, digest attributes, and
  signing metadata. No archive entry is under `META-INF/versions/`, and no
  case-insensitive signature-related entry `META-INF/*.SF`, `META-INF/*.RSA`,
  `META-INF/*.DSA`, `META-INF/*.EC`, or `META-INF/SIG-*` is present.

The descriptor records the exact manifest byte length, two or three main
attributes, zero or one `Created-By`, zero individual sections, and zero
unsupported main attributes. Existing dedicated counts for class path,
multi-release, launcher agent, signature version, versioned entries, and
signature-related entries remain zero; the allowlist, rather than that
illustrative set, is authoritative.

The finalizer launches with Java's `-jar` mode and must not add `-cp`,
`-classpath`, `--class-path`, a `CLASSPATH` environment variable, a wildcard
class path, or another application JAR. This is the exact meaning of
`classpathMode = jar-only`. The bound Java platform modules remain available
and are outside the JAR scan.

## Complete class-file scan

The class sub-policy identifier is
`jvms-se21-complete-class-file-v1`.

Every decompressed regular entry whose name ends in `.class` is parsed as one
complete class file. The parser validates `0xCAFEBABE`, minor and major
versions, constant-pool tags and double-slot rules, indexes, interfaces,
fields, methods, and all length-delimited attributes. Known attributes are
parsed according to the Java SE 21 grammar; an unknown attribute is skipped
only after its declared length has been bounds-checked and fully consumed.
The outer parser must finish exactly at entry EOF. A successful prefix parse is
not sufficient.

The descriptor records exact class count and observed major-version extrema.
`structuralParseFailureCount`, `trailingByteCount`, and
`nonZeroMinorVersionCount` must be zero.

### Rejected native and process surfaces

All methods in all classes are inspected. Any method with `ACC_NATIVE` is
rejected.

Every `CONSTANT_Class`, `CONSTANT_Methodref`,
`CONSTANT_InterfaceMethodref`, and resolved `CONSTANT_MethodHandle` target is
inspected, whether or not bytecode appears to reach it. The scanner also parses
and inspects every class type in field and method descriptors,
`CONSTANT_NameAndType`, `CONSTANT_MethodType`, signatures, annotations, record
components, and every other standard Java SE 21 type-bearing attribute.
Internal names use `/`. The following direct symbolic references are rejected:

- native loading: `java/lang/System.load`,
  `java/lang/System.loadLibrary`, `java/lang/Runtime.load`,
  `java/lang/Runtime.loadLibrary`, and members of
  `jdk/internal/loader/NativeLibraries`;
- foreign-function APIs: any class under `java/lang/foreign/` or
  `jdk/incubator/foreign/`;
- JNA and JNR: any class under `com/sun/jna/` or `jnr/`;
- process creation: `java/lang/Runtime.exec`, constructors or `start` /
  `startPipeline` methods of `java/lang/ProcessBuilder`, and
  `java/lang/ProcessImpl.start`.

The exact zero-valued result fields are
`accNativeMethodCount`, `nativeLoadMethodReferenceCount`,
`foreignApiTypeReferenceCount`, `jnaTypeReferenceCount`,
`jnrTypeReferenceCount`, `processLaunchMethodReferenceCount`, and
`forbiddenMethodHandleTargetCount`. A matching method-handle target is counted
in the relevant category and in the method-handle field; both must be zero.

This check is intentionally about direct symbolic references. It does not
claim to resolve strings passed to reflection, `invokedynamic` behavior beyond
its statically resolved method-handle targets, dynamically defined classes, or
symbols decoded or assembled at runtime.

### Executable-JAR compatibility gate before profile freeze

The process-reference invariant is not weakened merely because a general Scala
distribution or fat-JAR merger includes an unused `scala.sys.process` class.
Before a JVM validator artifact can be frozen, the exact intended Java 21 build
must pass this executable gate:

1. Execute the descriptor's `application-intermediate` phase twice, in two
   fresh JVM build-runner instances with distinct fresh output roots, from the
   same bound source, dependency, toolchain, build-JDK, and environment
   closures. Each instance is invoked with the phase's exact executable and
   ordered arguments and must produce `/out/application.jar`. The two JARs
   must be byte-for-byte equal and equal the descriptor's
   `packaging.applicationInput` identity before packaging begins.
2. Execute the descriptor's `copy-only-packaging` phase twice in two further
   fresh instances. Each invocation receives a newly materialized, read-only
   `/phase-input` tree under policy
   `eip0045-b4-jvm-copy-only-phase-input-v1`, a distinct fresh output root, and
   no source-tree or broad dependency-closure mount. The packager executable is
   the descriptor's unique bound `packager` and its ordered argument vector is
   exactly:

   ```text
   replay-copy-only-v1
   --manifest
   /phase-input/inclusion-manifest.json
   --archive-root
   /phase-input/archives
   --output
   /out/validator.jar
   ```

   Both outputs must be byte-for-byte equal and equal the manifest and
   descriptor output identities.
3. Apply this complete policy to both output JARs and emit a deterministic report for
   every forbidden symbolic reference as
   `(entry name, class internal name, constant-pool index, category, owner,
   member, descriptor)`, sorted by unsigned UTF-8 bytes and then numeric index.
   A nonempty report fails the candidate even if a reachability analysis calls
   the reference unused.
4. Launch each passing artifact through the exact JVM verification runner and
   CLI against the positive smoke fixture. A successful scan without an
   executable `Main-Class`, or a successful launch of bytes other than the
   scanned JAR, does not pass.
5. Only the replayed, inspected, and launched output JAR may populate the
   descriptor and acceptance record.

The phase order is normative: both application builds are completed, compared,
and bound before either packaging invocation. Every phase repetition uses a
new OCI instance and a new output root; every packaging repetition also uses a
new phase-input tree. Neither a whole-pipeline repetition nor reuse of one
container across phases satisfies this gate.

### COPY-ONLY packaging phase-input layout

The finalizer materializes exactly this tree for each packaging repetition:

```text
/phase-input/
  inclusion-manifest.json
  archives/
    application.jar
    dependency-000.jar
    dependency-001.jar
    ...
```

`inclusion-manifest.json` is the exact JCS document bound by
`packaging.inclusionManifest`. `archives/application.jar` is the validated
application-phase output and equals `packaging.applicationInput`.
`archives/dependency-NNN.jar` equals both manifest input `dependency-NNN` and
dependency-closure entry `NNN`, in descriptor order. The evidence-relative
`path` inside a manifest input does not select its container filename.

Only the manifest, the `archives` directory, and the exact regular files above
are present. Links, hardlinks, aliases, additional entries, and name-derived
fallbacks reject. The finalizer measures every file before launch and after
exit, destroys the staging tree after that repetition, and never lets the
packager discover an input through an environment variable, working-directory
default, source path, or dependency path.

This gate is deliberately pre-freeze: source availability or a working library
verifier is not evidence that a policy-conforming executable JAR exists. A
candidate remains pending until the exact built bytes pass all five steps.

### COPY-ONLY packaging manifest

The artifact `packaging` projection has policy
`eip0045-b4-jvm-copy-only-packaging-v1`, mode
`copy-only-inclusion-manifest`, application selection
`all-regular-entries`, dependency selection `reviewed-exact-copy-list`, and
replay policy `exact-input-output-entry-replay-required`. Its `packer` is byte
identical to the descriptor's unique `toolchainClosure` entry with role
`packager`; its `configuration` is byte identical to one exact
`implementationLineage.sourceFiles` entry. The latter is the reviewed
selection configuration, not an unreviewed reachability claim.

The separately supplied canonical JCS document has format
`Eip0045B4JvmCopyOnlyInclusionManifestV1` and is bound by exact path, byte
length, SHA-256, and encoding in the descriptor. It is at most 1 MiB and
contains at most 4,096 output entries. Its closed members are:

- policy `eip0045-b4-jvm-copy-only-packaging-v1`;
  `applicationSelection = all-regular-entries`;
  `dependencySelection = reviewed-exact-copy-list`;
  `inputArchivePolicy = eip0045-b4-jar-source-read-v1`; and
  output `archivePolicy = eip0045-b4-canonical-jar-zip-v1`;
- ordered `inputs`: the application intermediate is first with ID
  `application`; it is followed, in descriptor order, by every
  `dependencyClosure.entries` artifact with IDs `dependency-000`,
  `dependency-001`, and so on. Path, byte length, SHA-256, encoding, JAR format,
  and measured regular-entry count are explicit. A dependency may contribute
  no output entry; it remains present and hash-bound for reproducibility;
- ordered `entries` of exact
  `(kind, name, sourceInputId, sourceEntryName, byteLength, sha256)`. Kind is
  `regular-file`; source and output names are equal, so relocation is
  forbidden; the one length and hash describe both the decompressed source
  bytes and output bytes;
- `generatedEntries`, which is exactly empty in v1; and
- `output`, which is byte-identical to the final JAR identity in the build
  descriptor.

`META-INF/MANIFEST.MF` is first. All remaining output names are strictly
increasing by unsigned ASCII bytes. Output names are unique byte-for-byte and
after ASCII lowercase folding; each `(sourceInputId, sourceEntryName)` is used
at most once. The manifest and derived `Main-Class` entry both come from the
application input. Every regular application entry is selected exactly once.
Dependency entries may be omitted only by the reviewed exact list; the
manifest does not prove that such an omission is functionally safe. Source
review and the differential test suite cover reflection, services, and other
dynamic resource selection.

### Source-JAR parser and physical replay

The input parser policy `eip0045-b4-jar-source-read-v1` consumes the exact
descriptor-bound bytes without extraction. It uses the classic ZIP bounds,
complete record-coverage rules, unsupported-feature exclusions, canonical name
and entry-type grammar, local/central agreement rules, signed descriptor form,
streaming decompression checks, and CRC-32 checks defined above. Consequently,
it rejects every prefix, suffix, gap, overlap, unreferenced record, multi-disk
field, ZIP64 form or sentinel, encryption feature, unsupported compression
method, malformed or ambiguous name, traversal, duplicate name, ASCII-case-fold
collision, link, and special file before exposing an entry.

The source policy is a closed language, not generic ZIP compatibility. Each
entry has exactly one of these four-field tuples, where `version-made-by` is the
complete 16-bit field:

| entry encoding | version-made-by | version-needed | flags | method |
| --- | ---: | ---: | ---: | ---: |
| stored | `0x000a` | `10` | `0x0800` | `0` |
| raw DEFLATE | `0x0014` | `20` | `0x0808` | `8` |

Disk-start, internal attributes, and external attributes are zero. Local and
central extra fields are both empty, except that the first entry may carry the
exact four bytes `fe ca 00 00` (little-endian header ID `0xcafe`, zero data
length) in both headers. No other extra-field byte is accepted. Archive and
entry comments are empty. The local and central DOS time fields are one opaque
`u16` value and the local and central DOS date fields are one opaque `u16`
value; the two headers must agree byte-for-byte, but the source parser does not
interpret either value as a calendar timestamp.

Source entry order need not place the manifest first and need not be sorted.
The central entries must nevertheless occur in the same order as their local
records, names remain canonical and unique under both byte and ASCII-case-fold
comparison, and directory markers obey the exact canonical trailing-slash,
zero-length, and zero-CRC rules above. These ordering and timestamp allowances
are the only source-header differences from the canonical output language.
Source metadata is never copied to the output.

The trusted finalizer then remeasures every input archive, requires every listed
source entry exactly once with the declared decompressed bytes, length, and
hash, and requires the application input to have no unlisted regular entry. It
writes source content bytes unchanged through an explicit canonical ZIP writer,
then reparses the output under the stricter output policy. The output contains
exactly the manifest entries in their manifest order, no directories, and no
extra, missing, relocated, or rewritten content. Entry count, total and maximum
uncompressed lengths, class/non-class partition, manifest length, derived
`Main-Class` entry, and final archive identity must equal the descriptor.

The semantic gate validates the canonical manifest and all descriptor
relations. That token alone does not attest physical replay: completion still
requires the finalizer executor to perform the bounded source reads, COPY-ONLY
write, output reparse, and before/after measurements above.

## Non-class entry scan

The resource sub-policy identifier is
`eip0045-b4-jvm-nonclass-scan-v1`. Every decompressed regular entry other than
a `.class` entry is read completely, including the manifest. Directory markers
are excluded. `regularEntryCount` records this exact set and must equal
`scannedEntryCount`.

### Forbidden names

Comparison is ASCII-case-insensitive. A regular entry is rejected when its
last path component has one of these executable, native, script, or nested
archive suffixes:

```text
.so, .so.<digits-and-dots>, .dll, .dylib, .jnilib, .a, .lib, .o, .obj,
.exe, .com, .bat, .cmd, .ps1, .sh, .bash, .zsh, .fish,
.jar, .zip, .war, .ear, .jmod, .tar, .tgz, .gz, .bz2, .xz, .zst
```

`forbiddenNameMatchCount` must be zero.

### Forbidden byte signatures

The scanner rejects the following signatures at their stated locations:

- native or executable at offset 0: ELF `7f454c46`; WebAssembly `0061736d`;
  Unix archive `213c617263683e0a`; Mach-O `feedface`, `cefaedfe`, `feedfacf`,
  `cffaedfe`, `cafebabe`, `bebafeca`, `cafebabf`, or `bfbafeca`;
- PE: `4d5a` at offset 0, a bounds-checked little-endian `e_lfanew` read at
  offset `0x3c`, and `50450000` at that target offset;
- nested archive at offset 0: ZIP `504b0304`, `504b0506`, `504b0708`, or
  `504b0102`; gzip `1f8b`; bzip2 `425a68`; xz `fd377a585a00`; zstd
  `28b52ffd`; 7z `377abcaf271c`; RAR4 `526172211a0700`; or RAR5
  `526172211a070100`;
- POSIX tar: `7573746172` at offset 257;
- script: shebang `2321` at offset 0;
- misnamed class: `cafebabe` at offset 0 in an entry not named `.class`.

For deterministic accounting, `ca fe ba be` in a non-class entry is classified
as a misnamed class before Mach-O-universal signatures are considered. Other
signature categories are independently counted if more than one matches the
same entry.

The corresponding zero-valued fields are
`nativeExecutableMagicMatchCount`, `nestedArchiveMagicMatchCount`,
`scriptMagicMatchCount`, and `misnamedClassMagicMatchCount`.

These signatures do not prove that arbitrary resource bytes are inert.
Compressed, encrypted, transformed, or assembled payloads and resource-driven
class or method selection remain source-review obligations.

## Required source-review complement

Before this policy can support B4 closure, the pinned reviewed source must be
checked for the surfaces the byte scan deliberately does not decide:

- reflection, custom class loading, method-handle construction from strings,
  service/provider loading, scripting engines, and dynamic class definition;
- bytecode or source generation;
- decoding, decrypting, decompressing, concatenating, or otherwise deriving a
  class, library, executable, command, or method name from data;
- resource content used to choose an implementation, provider, class, method,
  executable, or command;
- delegation to native or process-launch facilities through wrappers whose
  forbidden reference appears outside the JAR;
- dependence on Java runtime native code beyond the ordinary execution surface
  explicitly inventoried and bound by the runner profile.

The review result is scoped to the exact source tree, dependency closure,
toolchain closure, JAR digest, and runner-profile commitments in the build
descriptor. The static scan is not a substitute for that review, and the
review is not a substitute for recomputing the static scan.

## Minimum negative fixtures

An implementation of V1 is not complete without isolated failures for at
least:

- ZIP64, encrypted, multi-disk, unsupported-extra-field, misplaced-JAR-marker,
  entry count 65,535, wrong version-needed/version-made-by, missing UTF-8 flag,
  wrong bit-3 policy, nonzero attribute, noncanonical DOS timestamp, local/
  central order drift, manifest not first, remaining-name order drift,
  prefixed, suffixed, gapped,
  overlapping, duplicate-name, ASCII-case-collision, traversal-name, link,
  unsupported-method, unsigned-descriptor, bad-CRC, size-mismatch, truncated
  DEFLATE, trailing-DEFLATE, per-entry-size, and cumulative-size cases;
- absent and duplicate manifest, absent and duplicate `Main-Class`, missing
